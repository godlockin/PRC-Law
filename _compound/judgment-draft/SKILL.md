# judgment-draft · 裁判文书起草 v2.0

**第一步必调 cn-legal-retrieval。所有法条引用格式：[schema:retrieval-hint:领域·子项]，不写死条号。**

> **v2.0 升级** (2026-08-02): 借鉴 gutachten-civil-case 的 W1/W2 双闸门 + Parthenon 的防泄漏原则 + Contract-Reviewer-Agent-Eval 的 ORCHESTRATOR 多 Agent 架构。从单线流程升级为多 Agent 并行 + 双闸门独立确认。

> ⚠️ **借鉴合规声明**: 本 skill 借鉴的均为公开方法论框架（双闸门、ORCHESTRATOR 多 Agent、防泄漏原则），**未引入**任何具体案件事实、当事人名称、判决原文。所有借鉴内容均注明来源仓库地址。W1/W2 双闸门方案非 PRC-Law 原创，原始设计来自 gutachten-civil-case，作者为游初（You Chu）。

## 角色

裁判文书起草 ORCHESTRATOR。以中立裁判视角，编排事实层→规范层→多 Agent 并行审查→汇总输出，按人民法院裁判文书格式（法发〔2016〕7号）生成初稿。

## 操作步骤

### W1 闸门: 事实层 + 设问识别

> **仅输出事实，禁止法律层**。这是借鉴 gutachten 的核心阀门约束。

1. 调用 cn-element-extraction：提取当事人、诉讼请求、答辩、证据、时间线、争议焦点（仅事实层面）
2. 整理"法律关系对"：X → Y 基于某种事实的对应关系（不含法律定性）
3. 列出待审设问（逐字引用当事人主张）
4. **W1 闸门检查**：
   - [ ] 输出仅含事实层（无条文号、无法律定性）
   - [ ] 法律关系对不含请求权结论
   - [ ] 设问引用当事人原话或诉状原文
   - [ ] 用户确认后进入 W2

**禁止跨阀门污染**：W1 阶段出现条文号 / 法律定性 / 争点预判 = 方法论违例，应回到 W1 重做。

### W2 闸门: 规范层（双层校验）

> **条文号、要件解释、法律关系定性** 仅从此阶段开始。

5. 调用 cn-legal-retrieval：先判断案由（民事/刑事/行政/执行）→ 检索实体法 + 程序法
6. 调用 cn-norm-verify：关键法条双源核验（请求权基础 / 时效 / 举证责任 / 程序事项）
7. 调用 cn-reasoning：识别请求权基础（侵权 / 违约 / 不当得利 / 无因管理 / 特殊侵权等）
8. 调用 cn-outcome-forecast：类案匹配 + 概率等级初判
9. **W2 闸门检查**：
   - [ ] 每个法条经 `[SLOT-LEGAL-DB]` 实时校验
   - [ ] 校验失败标注 `[⚠ 校验失败：<原因>，请人工核对]`
   - [ ] 校验记录写入 `verification-log.md`
   - [ ] 用户确认后进入 W3

**法条校验铁律**：
- 模型对法条的训练记忆不得作为引用依据
- 用户知识库中的 OCR 文本仅作初稿参考，最终以数据库返回原文为准
- 同一条文首次引用必须校验，后续引用可复用该次校验结果

### W3 多 Agent 并行审查

#### Agent-1 · 证据审查（cn-evidence-evaluation）

**职责**: 三性审查（真实性 / 合法性 / 关联性）+ 证明力分级 + 证明标准判断

**输出**:
| # | 证据 | 真实性 | 合法性 | 关联性 | 证明力 | 采信结论 |
|---|------|--------|--------|--------|--------|---------|

#### Agent-2 · 法律适用（cn-reasoning）

**职责**: 请求权基础识别 + 要件涵摄 + 演绎推理

**输出**:
- 原告请求权基础：[类型] + 法条 + 满足要件
- 被告抗辩：抗辩类型 + 法条 + 成立要件
- 法院认定：基于证据的要件涵摄

#### Agent-3 · 攻防对抗（cn-argument-chain）

**职责**: 原告诉求 / 被告抗辩 / 反诉 / 一事不再理

**输出**:
| # | 争议焦点 | 原告主张 | 被告抗辩 | 反诉/再抗辩 | 法院判断方向 |
|---|---------|---------|---------|----------|------------|

#### Agent-4 · 后果推导（cn-consequence-conflict）

**职责**: 责任性质 + 赔偿区间 + 合同效力

**输出**:
- 责任分析（违约/侵权/刑事/行政）
- 赔偿区间（区间而非点值）
- 风险分叉推演（最有利/最可能/最不利）

#### Agent-5 · 结果预测（cn-outcome-forecast）

**职责**: 类案匹配 + 概率等级 + 周期预估

**输出**:
- 类案匹配度
- 概率等级（高度可能/可能/不确定/不太可能）
- 诉讼周期预估

### W4 汇总与裁判文书初稿

10. ORCHESTRATOR 汇总 5-Agent 输出
11. 调用 cn-argument-chain：构建完整 Toulmin 论证链
    - Claim（主张）+ Grounds（事实根据）+ Warrant（推理依据）+ Backing（法理支撑）+ Rebuttal（反驳预判）+ Qualifier（限定条件）
12. 调用 cn-source-label：每条主张标注六态来源标签 + 时间戳
13. 校验 verification-log.md：法条准确性维度比对
14. 按法发〔2016〕7号 格式渲染裁判文书初稿

## 防泄漏原则（借鉴 Parthenon rubric-blind）

**禁止在裁判文书中包含**：
- ❌ 来自训练记忆的具体条文号（必须经数据库校验）
- ❌ 来自类似案件的事实细节
- ❌ 来自具体当事人的私域信息

**允许包含**：
- ✅ 通用法律框架引用
- ✅ 法条类型 / 制度名称（不含具体条号）
- ✅ 程序性表述

## 特殊注意事项

- **W1/W2 闸门不可合并**：借鉴 gutachten 明确要求——两闸门必须分别用 AskUserQuestion 单独拍板
- **ORCHESTRATOR 角色中立**：裁判文书必须中立，超出当事人诉求的部分应不予支持
- **Toulmin 论证的强制性**：每个争议焦点的论证都必须用 cn-argument-chain 的六要素构建
- **法条校验铁律**：缺数据库校验时整个文书不能标注 [已确认]
- **MCP 降级**：cn-legal-retrieval / cn-norm-verify 不可用时，所有法条标 `[模型知识—需验证]`，文书顶部渲染"⚠️ 检索服务不可用"风险横幅
